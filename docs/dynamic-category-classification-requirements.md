# 个人 Wiki 动态分类与 AI 归类确认需求文档

> 文档版本：1.0
> 文档日期：2026-08-14
> 文档状态：需求已确认，可进入开发
> 适用范围：每个用户的私有 Wiki 空间
> 需求性质：现有产品的增量功能，不是总 PRD 的完整实施任务

## 0. 开发范围声明

本文件只描述“个人 Wiki 动态分类、AI 归类建议、用户批量确认、磁盘目录同步和外部文件变更对账”这一部分需求。

开发本需求时：

- 不要把根目录 `PRD.md` 的全部内容当成本次开发任务。
- 不要重新实现用户系统、租户隔离、Wiki 广场、投稿审核或 Admin 后台。
- 保留现有用户系统、Raw 原料箱、生成任务、编辑、治理、事务、回滚和 Wiki 广场行为。
- 仅在动态分类需要接入现有能力时做最小范围修改。
- 本文件替换总 PRD 中“分类固定”“生成时直接落入固定分类目录”“原料摄入时必须先选择正式分类”的相关规则；总 PRD 的其他规则继续有效。

## 1. 背景与问题

当前实现使用全局固定分类目录。分类在代码中写死，生成前通过术语、来源路径和局部上下文选择一个分类，分类又直接决定 Markdown 文件路径。

这会带来以下问题：

1. 原料内容只能被映射到预设分类，用户不能让自己的分类体系随知识增长。
2. AI 在正文生成前只看到有限上下文，容易把词条放入错误分类。
3. 用户确认分类时只能从固定列表选择，现有分类都不合适时无法原地创建。
4. 预先创建正式分类目录会产生空目录、一次性目录和含义重复的目录。
5. 分类同时影响应用导航和磁盘路径，错误归类后的移动容易影响链接、Raw 关联、任务和历史记录。
6. 用户直接在文件系统中新建、移动或重命名目录时，应用无法安全判断这是有意调整还是误操作。

## 2. 产品目标

建立一套以用户确认为最终决策、由 AI 尽量完成整理工作的个人动态分类系统。

目标结果：

1. 每个用户空间拥有独立的一级分类体系。
2. 分类在文件系统中表现为真实目录，并同步用于应用侧栏导航。
3. 每个词条只有一个主分类，可以拥有多个标签。
4. 原料投入后，AI 只展示预计分类方案，不创建正式分类目录。
5. 新词条生成完成后，AI 根据完整正文重新推荐分类和标签。
6. 用户通过一次批量确认完成分类，可接受推荐、改选分类或立即创建新分类。
7. 高置信度推荐可以批量接受，但任何实际移动仍需用户显式确认。
8. 分类重命名时同步重命名磁盘目录。
9. 应用检测文件系统外部变更，但未经用户确认不得自动采纳。
10. 所有批量移动、目录重命名和链接更新都必须可预览、原子执行并支持回滚。

## 3. 非目标

第一版不包含：

- 二级或更深的分类目录。
- 一个词条同时存放在多个分类目录。
- 未经用户确认自动移动词条或创建正式分类。
- 跨用户共享分类样例或训练数据。
- 自动采纳文件系统中的目录移动、重命名或删除。
- 直接删除仍包含词条的分类。
- 改造 Wiki 广场的公共分类体系。
- 因本需求重新设计投稿、审核、账号或权限系统。
- 为实现分类而引入向量数据库或跨空间语义索引。

## 4. 已确认的产品决策

| 议题 | 决策 |
|---|---|
| 分类层级 | 第一版只支持一级分类 |
| 词条归属 | 一个主分类，多个标签 |
| AI 自动化程度 | AI 尽量推荐，用户最终确认 |
| 无合适分类 | 用户可在确认界面立即创建新分类 |
| 原料投入阶段 | 只展示预计分类方案，不创建目录 |
| 正式创建目录时机 | 词条生成后，经用户批量确认时统一创建 |
| 高置信度推荐 | 允许用户一键接受全部，默认阈值为 85% |
| 分类重命名 | 同步重命名磁盘目录 |
| 现有“未分类”词条 | 只标记待确认，不立即移动 |
| 外部文件系统变更 | 检测后提示用户确认，不自动采纳 |
| 非空分类删除 | 禁止；必须先迁移词条或归档分类 |

## 5. 核心概念

### 5.1 正式分类

用户已经确认并在磁盘中拥有真实目录的分类。正式分类用于：

- 决定词条的主目录。
- 组织应用侧栏导航。
- 作为 AI 后续归类的候选分类。
- 提供分类说明、别名和代表词条作为个人样例。

### 5.2 预计分类方案

AI 在原料投入后，根据原料全文给出的临时分类规划。预计分类方案可以包含：

- 建议分类名称。
- 分类用途说明。
- 预计归入的候选词条。
- 预计词条数量。
- 与现有分类的相似性提示。
- 置信度。

预计分类方案不是正式分类，不创建目录，不进入侧栏，也不能作为已确认归类写入词条。

### 5.3 归类建议

词条正文生成完成后，AI 基于完整正文和当前用户分类体系生成的结构化建议。每个词条最多包含：

- 一个首选现有分类。
- 两个备选现有分类。
- 每个候选分类的置信度和简短理由。
- 推荐标签。
- 必要时给出一个新分类建议及说明。

### 5.4 待归类目录

系统保留目录：

```text
wiki/_inbox/
```

凡是新建正本但尚未确认主分类的词条，都先进入该目录。`_inbox` 不是普通分类，不能重命名、归档或删除。

### 5.5 标签

标签用于表达跨分类主题，不创建磁盘目录。标签应优先复用当前用户已有标签，并对大小写、全半角、首尾空白和明显同义写法进行规范化提示。

## 6. 信息架构与逻辑数据模型

以下是必须具备的逻辑字段，不强制指定使用 SQLite、JSON 还是其他现有持久化方式。数据必须以当前服务端会话解析出的 `workspace_id` 隔离。

### 6.1 Category

| 字段 | 说明 |
|---|---|
| `category_id` | 稳定且不可复用的分类 ID |
| `workspace_id` | 所属私有空间，只能由服务端会话确定 |
| `name` | 用户看到的分类名称 |
| `directory_name` | 对应一级磁盘目录名；重命名分类时同步变化 |
| `description` | 分类用途说明，供用户和 AI 判断 |
| `aliases` | 可选的分类别名 |
| `status` | `active` 或 `archived` |
| `sort_order` | 侧栏排序 |
| `created_at` / `updated_at` | 审计时间 |

约束：

- `category_id` 不因分类改名或目录改名而变化。
- 分类名称在同一空间内按 Unicode 规范化和不区分大小写后唯一。
- 用户分类目录只能是 `wiki/` 下的一级目录。
- 禁止使用 `_inbox`、`.`、`..`、`index.md`、`log.md` 及其他系统保留名。
- 名称中不得包含 `/`、`\`、NUL 或会造成路径逃逸的字符。
- 分类记录必须随空间导出和迁移，不能只存在于平台全局状态中。

### 6.2 Article 分类字段

| 字段 | 说明 |
|---|---|
| `article_id` | 稳定词条 ID，移动或改名后保持不变 |
| `primary_category_id` | 已确认主分类；待归类时为空 |
| `tags` | 零到多个标签 |
| `classification_status` | `pending`、`confirmed` 或 `sync_conflict` |
| `classification_updated_at` | 最近一次确认或对账时间 |

Markdown 和应用索引中必须能够恢复稳定 `article_id`。现有以路径为主键的状态记录需要在移动时通过 `article_id` 或统一重映射保持一致。

### 6.3 ClassificationSuggestion

至少包含：

- `article_id`
- 建议生成版本或正文 revision
- 最多三个现有分类候选
- 每个候选的 `category_id`、置信度和理由
- 推荐标签
- 可选的新分类建议
- 建议状态：待确认、已接受或已忽略
- 创建时间和使用的分类体系版本

正文 revision 改变后，旧建议不得被静默应用；需要重新计算或要求用户重新确认。

### 6.4 FilesystemReconciliation

用于记录扫描发现但尚未确认的文件系统变化：

- 新建分类目录。
- 分类目录重命名。
- 词条被移动到其他分类目录。
- 分类目录被删除。
- 词条元数据与所在目录不一致。

每项记录需要保存检测到的路径、已有逻辑记录、建议动作和处理状态。

## 7. 状态机

### 7.1 词条归类状态

```text
新词条生成完成
      |
      v
   pending ----------------------+
      | 用户确认                  | 用户暂不处理
      v                           |
  confirmed <---------------------+
      |
      | 检测到外部移动、目录改名或元数据冲突
      v
 sync_conflict
      |
      | 用户选择采纳磁盘变更或恢复应用记录
      v
  confirmed
```

### 7.2 分类状态

```text
active <------ 用户恢复 ------ archived
  |                                ^
  | 用户归档                        |
  +--------------------------------+

active 或 archived 只有在目录为空、无词条引用且通过预检时才可删除。
```

归档分类：

- 保留磁盘目录和所有词条。
- 词条仍可搜索和打开。
- 默认不显示在主侧栏。
- 不出现在新词条的常规分类选择器中。
- AI 不得将其作为首选或备选分类。
- 用户可在分类管理页查看并恢复。

## 8. 详细用户流程

### 8.1 原料投入与预计分类方案

1. 用户向原料箱添加文档。
2. 系统保持 Raw 原文不可变，并完成现有解析、OCR 和完整性检查。
3. AI 或本地降级逻辑分析原料全文，生成预计分类方案。
4. 页面展示预计分类、说明、预计词条和置信度。
5. 此时不得创建 `wiki/<候选分类>/` 目录，也不得修改正式分类列表。
6. 页面明确说明：最终分类会在词条正文生成后重新判断，可能与预计方案不同。
7. 用户可以继续生成，也可以关闭页面；预计方案可恢复，但不能阻塞 Raw 浏览。

### 8.2 新词条生成

适用于从 Raw 新建、采用为种子或从概念生成的全新正本：

1. 生成任务沿用现有持久队列，远端模型或网络失败不得阻塞其他本地操作。
2. 新正本生成完成后先写入 `wiki/_inbox/<filename>.md`。
3. 词条标记为 `classification_status=pending`，不写入任意正式主分类。
4. 词条可以立即打开、编辑和搜索，并在侧栏“待归类”区域显示。
5. 对已有正本执行“补充”时，保留其现有主分类，不强制进入待归类。
6. 如果生成失败，不创建空分类目录；任务按现有规则显示失败并可重试。

### 8.3 完整正文归类

词条生成完成后，系统使用以下上下文产生归类建议：

- 完整生成正文，而非只使用标题或局部段落。
- 当前用户所有 `active` 分类的名称、说明、别名和代表词条。
- 当前用户已有标签。
- 当前用户过去确认和纠正过的归类样例。
- 当前 Raw 来源和生成上下文的必要摘要。

AI 输出必须经过结构化解析和枚举校验，不能直接把模型返回的路径、分类 ID 或标签写入文件系统。

当个人模型未配置、调用失败或返回非法结构时：

- 词条继续保留在 `_inbox`。
- 使用本地启发式给出低置信度建议，或只允许手工选择。
- 显示真实失败状态和重试入口。
- 不得因为分类服务不可用而丢失或隐藏已生成正文。

### 8.4 归类工作台

工作台按以下分组展示待确认词条：

1. **高置信度推荐**：首选分类置信度不低于 85%。
2. **需要确认**：多个分类分数接近或首选低于 85%。
3. **建议新建分类**：现有分类明显不适用。
4. **归类失败**：AI 不可用或建议无法解析。

每个词条卡片至少展示：

- 标题和正文摘要。
- 首选分类、最多两个备选分类。
- 置信度和推荐理由。
- 推荐标签。
- 新分类建议。
- 当前文件路径。

用户可以：

- 接受首选分类。
- 改选其他已有分类。
- 搜索全部 `active` 分类。
- 修改、增加或删除标签。
- 在当前界面创建新分类。
- 暂不处理，让词条继续留在 `_inbox`。
- 多选词条后批量指定同一主分类或标签。

### 8.5 接受全部高置信度推荐

1. 系统默认勾选首选置信度不低于 85% 的词条。
2. 用户点击“接受全部高置信度推荐”只是形成待提交选择，不立即移动文件。
3. 提交前必须展示最终变更清单，包括：
   - 将创建的分类目录。
   - 每个词条的源路径和目标路径。
   - 将写入的主分类和标签。
   - 将更新的链接、索引和关联记录数量。
   - 文件名或目录冲突。
4. 用户显式确认后才执行事务。
5. 低于 85%、存在冲突或建议新分类但未确认名称的词条不得被批量静默处理。

### 8.6 原地创建新分类

用户在归类卡片或批量工具栏中可以创建新分类，无需离开页面。

交互要求：

- 用户输入分类名称。
- AI 可以预填分类说明，但用户可编辑。
- 系统提示同名、近似名称和别名冲突。
- 用户仍可在不存在精确冲突时确认创建相近分类。
- 新分类只有在整批归类事务提交时才成为正式分类并创建目录。
- 用户取消批量确认时，不留下空目录或半完成分类记录。
- 没有被最终采用的预计分类和新分类建议不得创建目录。

### 8.7 分类重命名

用户重命名分类时必须同步重命名磁盘目录。

执行前展示：

- 原分类名和新分类名。
- 原目录和目标目录。
- 受影响词条数量。
- 需要更新的站内链接、Raw 目标、任务或状态记录数量。
- 目标目录是否已存在。
- 应用外保存的旧路径可能失效的提示。

一次重命名事务至少覆盖：

- 分类记录与目录名。
- 分类目录及其中词条路径。
- 词条分类元数据。
- 全库受管理 Markdown 相对链接。
- Raw `linked_target` 等路径关联。
- 搜索索引、侧栏索引和日志。
- 路径关联的任务、幂等结果和可回滚操作记录；不能更新的历史记录需通过稳定 ID 保持可追溯。

分类和词条稳定 ID 在重命名后不得变化。

### 8.8 分类归档与删除

- 非空分类禁止直接删除。
- 用户可以将非空分类归档，目录和词条保持原位。
- 用户可以先批量迁移词条，再删除空分类。
- 删除前必须检查目录是否真正为空、是否存在隐藏或未知文件、是否仍有词条或状态引用。
- 存在未知文件时禁止删除，并引导用户处理。
- 删除空分类也必须产生 operation ID 并可在现有事务能力允许的范围内回滚。

### 8.9 文件系统外部变更对账

应用启动、用户点击重新扫描或相关目录发生变化后，系统检查：

- 新增一级目录。
- 已登记分类目录消失，同时出现可能的重命名目录。
- 带稳定 `article_id` 的词条出现在其他目录。
- 词条主分类元数据与所在目录不一致。
- 目录或文件名发生规范化冲突。

检测结果不得自动写入分类记录或修改 Markdown。用户必须选择：

1. **以文件系统为准**：注册新分类、采纳目录改名或更新词条主分类。
2. **恢复应用记录**：将目录或词条恢复到应用记录的位置。
3. **暂不处理**：保持 `sync_conflict`，禁止依赖旧路径的破坏性操作。

如果目标路径存在同名文件或内容冲突，系统必须阻止同步，让用户选择重命名、合并或取消。禁止静默覆盖或自动添加数字后缀。

## 9. 文件与目录规则

目标结构示例：

```text
wiki/
  _inbox/
    用户访谈.md
  用户研究/
    需求验证.md
  产品策略/
    最小可行产品.md
  index.md
  log.md
```

规则：

- 用户分类均为 `wiki/` 的直接子目录。
- 一个词条文件只能位于 `_inbox` 或一个正式分类目录中。
- 分类目录名与用户可见分类名同步；重命名分类必须同步目录。
- 路径解析必须拒绝绝对路径、`..`、符号链接逃逸和 Unicode 混淆后的重复路径。
- 文件移动不得跨用户空间。
- 目录扫描不得把 `index.md`、`log.md`、事务历史、缓存或隐藏运行时目录识别为分类。
- 应用应使用稳定 ID 识别词条和分类，不得只依赖可变路径建立长期引用。

## 10. AI 推荐规则

### 10.1 输出结构

归类模型输出必须转换为受控结构，至少包含：

```json
{
  "article_id": "stable-id",
  "recommendations": [
    {
      "category_id": "existing-category-id",
      "confidence": 0.91,
      "reason": "正文主要讨论用户访谈和需求验证"
    }
  ],
  "tags": ["访谈", "需求发现"],
  "new_category": {
    "name": "用户研究",
    "description": "围绕用户需求发现、访谈、观察和验证的知识"
  }
}
```

模型输出中的 `category_id` 必须属于当前空间的 `active` 分类。标签和新分类名称必须经过长度、字符、重复和路径安全校验。

### 10.2 个人化学习

用户每次接受或修改分类时，记录为当前空间的分类样例。后续推荐可使用：

- 用户最终选择的分类。
- 被否决的 AI 首选分类。
- 确认后的标签。
- 分类说明和代表词条摘要。

这些信息不能跨用户共享，不能出现在 Admin 后台或 Wiki 广场投稿快照中。

### 10.3 后台执行

- 预计分类分析和正文归类均进入本地持久任务队列。
- 网络或模型失败时允许断网继续使用应用，并支持后台重试。
- 同一正文 revision 的重复请求应幂等，避免重复消耗模型和产生不同建议覆盖用户选择。
- 用户已经确认归类后，后台迟到的旧建议不得覆盖当前分类。

## 11. 应用界面要求

### 11.1 原料预览页

新增“预计分类方案”区域，展示候选分类、说明、预计词条和置信度，并明确标注“仅为预览，尚未创建目录”。

### 11.2 侧栏

- 顶部或治理区显示“待归类”及数量。
- 普通区域只展示 `active` 分类。
- 归档分类默认隐藏，可从分类管理页进入。
- 分类名称变化后，侧栏和深链状态在事务完成后统一刷新，不能出现新旧名称并存。

### 11.3 归类工作台

提供适合批量扫描的表格或列表，不使用逐词条强制弹窗。必须支持：

- 分组查看。
- 多选和全选高置信度推荐。
- 内联改分类、建分类和改标签。
- 冲突提示。
- 最终变更预览。
- 提交进度、成功结果和 operation ID。
- 整批撤销入口。

### 11.4 分类管理页

支持：

- 查看 active / archived 分类。
- 创建、重命名、排序、归档和恢复分类。
- 查看每个分类的词条数量。
- 批量移动分类中的词条。
- 仅在分类为空且无未知文件时删除。
- 查看近似分类提示，但不自动合并。

### 11.5 外部变更对账页

对每项变更展示应用记录、磁盘现状、影响文件和三个动作：采纳、恢复、暂不处理。用户作出选择前，不得用不明确的“自动修复”按钮代替决策。

## 12. 与现有功能的集成边界

### 12.1 Raw 原料箱

- 保持 Raw 原文不可变、hash 校验、解析和 OCR 行为。
- 原料处理页不再要求用户在正文生成前选定一个永久分类。
- 对已有正本执行补充时，仍关联原正本，不创建新的待归类副本。

### 12.2 生成任务

- 现有本地优先、远端补证、任务重试和重启恢复保持不变。
- 生成任务成功和归类任务成功是两个独立状态。
- 生成成功但归类失败时，正文仍然可用。

### 12.3 编辑与治理

- 用户可编辑 `_inbox` 中的词条。
- 正文改变后，只使基于旧 revision 的归类建议失效，不应丢失编辑。
- 已确认词条仍可通过治理入口修改主分类，但应复用同一事务搬迁和预览能力。

### 12.4 搜索、链接和反链

- `_inbox` 词条参与当前私有空间搜索，但结果标记“待归类”。
- 词条移动后，应用内链接和反链继续指向同一 `article_id`。
- 受管理的 Markdown 相对链接必须随移动重写。
- 应用无法保证修复用户在其他应用中保存的旧磁盘路径，因此重命名前必须提示。

### 12.5 Wiki 广场

- 私人分类与广场公共分类相互独立。
- 投稿快照可以携带私人分类名称和标签作为审核上下文，但不能暴露私有目录路径或 `workspace_id`。
- 本需求不改变广场分类、AI 初审或 Admin 审核状态机。

## 13. 迁移要求

迁移现有空间时：

1. 为现有固定分类创建当前空间内的动态分类记录，保留现有目录和中文显示名。
2. 为所有正本补齐稳定 `article_id`，且不得改变正文语义、标题、别名或来源。
3. 位于普通现有分类目录中的词条标记为 `confirmed`。
4. 位于现有“未分类”目录中的词条只标记为 `pending`，文件保持原位，不立即移动到 `_inbox`。
5. 这些待确认词条在工作台中显示“历史未分类”，用户确认后才执行目录移动。
6. 固定分类目录迁移完成后可以继续作为该用户的正式分类，但固定代码目录不得继续充当动态分类的验证白名单。
7. 新用户空间不因预计分类方案自动创建正式目录；正式目录在首次批量确认时产生。
8. 迁移必须包含备份、源文件 hash、目标校验、迁移 manifest 和失败回滚。
9. 多用户环境中逐空间迁移，任何空间失败不能污染其他空间。

## 14. 异常与冲突处理

| 场景 | 预期行为 |
|---|---|
| AI 不可用 | 保留待归类，允许手工选择和重试 |
| 建议引用不存在的分类 | 拒绝该建议，显示归类失败，不创建目录 |
| 正文在确认前被编辑 | 旧建议失效，要求重新分析或手工确认 |
| 目标目录已存在但未登记 | 进入文件系统对账，不能直接覆盖 |
| 目标文件同名 | 阻止整批提交，要求重命名、合并或取消 |
| 目录名规范化后重复 | 阻止创建或重命名 |
| 批量事务中途失败 | 恢复所有 before-image，不留下空目录或部分移动 |
| 用户关闭页面 | 选择和建议持久保存，文件留在原处 |
| 后台旧任务迟到 | 不得覆盖较新的正文 revision 或用户确认结果 |
| 分类包含未知隐藏文件 | 禁止删除并展示具体文件 |
| 外部删除分类目录 | 标记冲突，不自动重建或删除逻辑分类 |

## 15. 权限、安全与隐私

- 所有分类、建议、标签、路径和任务只能访问当前会话所属空间。
- API 不接受客户端指定的 `workspace_id` 或 `owner_id` 作为授权依据。
- 分类 ID、文章 ID、任务 ID、operation ID 和对账记录都必须做跨租户 IDOR 测试。
- AI 只接收完成归类所需的当前词条、分类说明和必要来源摘要；不得上传整个私有空间。
- AI 输出、目录名、标签和 Markdown 均视为不可信输入。
- 所有路径操作继续使用现有安全解析、符号链接逃逸检查、锁、原子写和事务回滚。
- 错误响应不得泄露其他空间是否存在同名分类、文件或词条。

## 16. 非功能要求

### 16.1 数据安全

- 分类批量确认、分类重命名、批量迁移和删除空分类均必须原子化。
- 每次提交返回 operation ID，并可查询变更 manifest。
- 回滚前验证当前文件 hash；文件已被后续修改时不得盲目覆盖。

### 16.2 可用性

- 无模型、断网或归类失败时仍能创建、阅读、编辑和手工归类词条。
- 批量工作台刷新或重启后恢复未提交选择和建议。
- 长时间 AI 分析不得阻塞原料箱、阅读页或编辑器。

### 16.3 性能

- 分类列表、待归类数量和侧栏不得为每次渲染全量读取所有正文。
- 批量工作台至少能流畅处理 500 个待归类词条和 100 个一级分类。
- 文件系统扫描应支持增量或缓存，不应在每次页面导航时同步全库扫描。

### 16.4 可访问性

- 分类选择、批量勾选、新建分类和冲突处理可通过键盘完成。
- 置信度不能只依赖颜色表达。
- 目录或文件冲突需要可读文本，不得只显示通用失败提示。

## 17. 建议接口能力

具体路由名称可沿用项目现有风格，但必须覆盖以下行为：

- 查询 active / archived 分类及词条数量。
- 创建分类、重命名分类、归档、恢复和删除空分类。
- 获取原料预计分类方案及任务状态。
- 获取待归类词条和结构化建议。
- 预览批量归类变更，不产生写入。
- 幂等提交批量归类并返回 operation ID。
- 获取文件系统对账项。
- 预览并提交“采纳磁盘”或“恢复应用”决策。
- 查询和回滚分类相关 operation。

所有写接口继续要求同源、CSRF、JSON、精确字段、请求体限制和 Idempotency-Key。

## 18. 验收标准

### 18.1 原料与预计方案

- [ ] 投入原料后可以看到预计分类方案。
- [ ] 预计方案产生时，磁盘中没有创建任何候选分类目录。
- [ ] 页面明确说明预计方案不等于最终分类。
- [ ] AI 失败不影响 Raw 原文和后续手工处理。

### 18.2 新词条与归类建议

- [ ] 新正本在确认前位于 `wiki/_inbox/` 并显示“待归类”。
- [ ] 补充已有正本不会产生新的 `_inbox` 副本。
- [ ] AI 使用完整正文，最多返回三个现有分类候选、置信度、理由、标签和可选新分类。
- [ ] 建议使用正文 revision；正文变化后旧建议不能提交。
- [ ] 无模型时用户仍可手工完成归类。

### 18.3 批量确认

- [ ] 用户可以一键选中全部首选置信度不低于 85% 的建议。
- [ ] 一键选择后仍需查看变更预览并显式确认。
- [ ] 用户可以逐词条改选分类、调整标签或暂不处理。
- [ ] 用户可以原地创建新分类并用于一个或多个词条。
- [ ] 未采用的分类建议不会产生目录或分类记录。
- [ ] 批量提交成功后，目录、文件、元数据、索引和链接保持一致。
- [ ] 批量提交失败时无部分移动、空目录或残留分类。
- [ ] 提交返回 operation ID，且可整批回滚。

### 18.4 分类管理

- [ ] 每个用户只能看到和管理自己的分类。
- [ ] 分类只支持一级目录。
- [ ] 重命名分类同步重命名磁盘目录。
- [ ] 重命名前展示受影响文件和冲突，成功后稳定 ID 不变。
- [ ] 非空分类不能删除。
- [ ] 非空分类可以归档，归档后目录和词条保留且 AI 不再推荐。
- [ ] 迁移完词条后可以删除真正为空的分类。
- [ ] 同名、规范化重复、保留名和路径逃逸名称被拒绝。

### 18.5 迁移与外部变更

- [ ] 现有固定分类转换为当前空间的动态分类，不移动已有普通分类词条。
- [ ] 现有“未分类”词条标记待确认，但文件保持原位。
- [ ] 手工新建目录、移动词条或重命名目录后，应用只产生对账提示。
- [ ] 用户可以选择以磁盘为准、恢复应用记录或暂不处理。
- [ ] 未确认前应用不会自动修改分类记录或 Markdown。
- [ ] 同名文件冲突会阻止同步，不会覆盖或自动追加数字后缀。
- [ ] 对账项、operation 和分类 ID 均通过双用户 IDOR 测试。

### 18.6 回归验证

- [ ] 现有非性能 Python 测试通过。
- [ ] 现有性能测试通过。
- [ ] 前端 lint、typecheck 和生产构建通过。
- [ ] 浏览器完成原料预览、生成、批量确认、新建分类、重命名、归档、回滚和外部变更对账流程。
- [ ] Raw 不可变、正文编辑冲突、正本合并、任务恢复、用户隔离和 Wiki 广场流程无回归。

## 19. 建议实施顺序

1. **稳定身份与动态分类基础**：Category、article_id、标签字段、空间隔离和迁移。
2. **待归类目录与兼容层**：`_inbox`、现有未分类标记、导航和搜索。
3. **预计分类与完整正文建议**：任务、结构化结果、失败降级和 revision 保护。
4. **归类工作台**：批量选择、内联新建分类、变更预览和事务提交。
5. **分类管理**：重命名、归档、恢复、空分类删除和批量迁移。
6. **文件系统对账**：外部目录和文件变化检测、采纳或恢复流程。
7. **回归与浏览器验收**：双用户隔离、冲突、回滚、离线和现有功能回归。

每一步都应有独立测试并保持现有主流程可用，不要等全部完成后才补数据迁移或回滚测试。

## 20. 完成定义

当且仅当以下条件同时满足，本需求才算完成：

1. 用户可以在不依赖固定分类白名单的情况下建立自己的一级分类体系。
2. 原料分析不会预创建正式目录。
3. 新词条先进入待归类区，用户可以批量确认 AI 建议或原地创建分类。
4. 主分类、标签、应用导航和磁盘目录一致。
5. 分类重命名、归档、迁移和外部变更对账具备明确、安全、可回滚的行为。
6. 现有未分类词条完成无移动迁移标记。
7. 跨租户、路径安全、并发、失败回滚和浏览器端到端测试通过。
8. 用户系统、Raw 原料、编辑、生成、Wiki 广场和审核流程没有回归。
